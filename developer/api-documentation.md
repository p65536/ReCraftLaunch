# Python拡張APIの記述と検証

利用者がPythonの基本知識とヘルプだけで独自機能を実装できることを、API説明の基準とする。説明の長さではなく、呼出し方と結果・制約を判断できる情報が揃っているかを確認する。

## 正本と範囲

- APIの個別契約は実装に隣接するDoxygenコメントに日英併記する。識別子と引数名は翻訳しない。
- 複数APIの組合せ、配置、適用、実行、診断の手順はdocs/ja・docs/enのPython拡張ガイドに置き、個別APIへリンクする。
- 実装・既存テストを契約の根拠とする。型注釈だけからNoneの可否、属性の存在、例外、呼出しスレッドを推定しない。ネイティブAPIは引数解析・Pythonへの変換・登録表も確認する。Python向けの署名・契約はネイティブソース内の専用ページにも記述できる。C++内部バインダーを利用者向けAPIとして公開せず、登録表と生成ページの掲載対応を検査する。
- 公開入口で再公開される名前、設定フックに渡るオブジェクト、公開の設定属性、コールバック用オブジェクトを調べる。内部のクラス・イベント配送を無条件に利用者向けAPIへ追加しない。
- 生成済みHTML・CSSを直接編集しない。生成方法と日英条件の書式は[文書生成手順](../tools/README-docs.md)に従う。

## 共通の記述基準

| 項目 | 必要な情報 |
|---|---|
| 用途・入口 | 何を実現するか、import名、インスタンスの取得元、使う場面 |
| 引数・属性 | 型、意味、単位・座標系・範囲、既定値、省略・None・空値の違い、読書きの可否 |
| 戻り値 | 型と意味、正常・取消・不成立の値、呼出し元が戻り値を使うか |
| コールバック | 正確な引数と戻り値の解釈、呼ばれるタイミング・スレッド、再入・保持の可否 |
| 前提・副作用 | 適用順、変更される状態、履歴・入力・ファイル・外部操作への影響 |
| 寿命・終了 | 登録解除、破棄、完了待ち、Reload・終了時の扱い、所有者 |
| 例外・制約 | 呼出し元へ届く例外、内部で通知される失敗、未実装・OS依存の範囲 |
| 例・関連項目 | 最小の使用例またはガイド内の完成例、代替API・関連APIへの参照 |

該当しない項目のためだけに空の見出しを増やさない。クラスに共通の利用手順を書き、各メソッドでは個別契約を補う。コンストラクターと公開属性も対象にする。複数経路で同じ型の値が異なる場合は経路ごとに説明する。戻り値Noneと属性の不在、終了要求と強制停止を区別する。

## 実装例

例には配置先、必要なコード全文、反映方法、実行入力またはキー、期待結果、無効化方法を付ける。既存custom.pyへの統合時は同じフックを重複定義させず、既存設定の必要な箇所へ追加する。importのキャッシュ、名前衝突、同名JSON登録、GUI一覧との違いを説明する。

原稿にあるコードブロックを直接取得して構文・登録・実行・取消等を検証する。テスト内に別の実装例を複製しない。代替オブジェクトによる契約検査、実Windowsの検査、ブラウザー表示・物理入力・実IME等の観察を区別する。例を成立させるために製品の挙動を変更しない。

## 生成とレビュー

`Python315/tools/python.exe -B makefile.py document`で日英を生成する。既存check_docs.pyに加え、追加した公開項目・例への導線と日英のAPI掲載対応を確認する。未記述メンバーを全公開する設定変更は、説明不足の解消にならない。

ネイティブのPython向け専用ページはckitcore.cppのckit_native、clnch_native.cppのclnch_native_api、pyautocore.cppのpyauto_native。check_docs.pyは実登録表から掲載を確認し、ckitの構築入口・通知・属性も照合する。個別のC++関数名や内部型をPythonの公開入口へ読み替えない。

リンク検査だけでは、説明の正しさや十分さは証明できない。上表に沿った実装との照合、原稿の例の実行、生成されたシグネチャ・引数表・コード表示を確認する。最終配布物にも同じヘルプと例が含まれることを[検証手順](release-verification.md)に従って確認する。
